# 定期実行のループ（daily-triage・handle-request）運用ガイド

Claude Code の予定タスク（claude.ai のクラウドの Routine）で走らせるループの運用に関する正（SSOT）です。
手順そのものの正はリポジトリのループ定義で、このドキュメントは「どう設定し、どう試し、結果をどう読むか」を書きます。

| 何 | 正となるファイル |
|---|---|
| 全ループに共通の枠（段階・Checker・報告の末尾・実行ログ） | [.claude/skills/run-loop/SKILL.md](../.claude/skills/run-loop/SKILL.md) |
| daily-triage の手順・制約・報告形式 | [.claude/loops/daily-triage.md](../.claude/loops/daily-triage.md) |
| handle-request の手順・触らないパス・検証役への指示文・行の更新 | [.claude/loops/handle-request.md](../.claude/loops/handle-request.md) |

## 1. ループの一覧

| ループ | 段階 | すること |
|---|---|---|
| `daily-triage` | **L1（読むだけ）** | 毎朝、Security Scan と CI の結果を仕分けて報告します。コードの変更・コミット・push・PR や Issue の作成・ワークフローの再実行は一切しません。直すのは人か、handle-request への依頼です。すでに依頼してある項目・確認済みの項目では騒ぎません |
| `handle-request` | **L2（検証役つきの修正）** | Notion の `DB_依頼` の依頼を 1 件、作業ブランチで直して `develop` 宛の PR にします。Checker（機械の検査と、書いた本人とは別のサブエージェント）が APPROVE を出したときだけ push します。人の判断が要るときは差し戻さずに質問して待ち（確認待ち）、PR がマージされた依頼を「完了」にします。**マージはしません** |

予定タスクの指示文は短く保ち、手順はリポジトリに置きます。指示文を変えずに、手順を PR でレビューして直せるようにするためです。
どのループも、結果を Notion の `DB_Claude 実行ログ` に 1 ページ残します。

## 2. daily-triage

| 項目 | 値 |
|---|---|
| 指示文 | `.claude/CLAUDE.md を読み、run-loop スキルで daily-triage を実行する` |
| リポジトリ | このリポジトリ（既定のブランチ `main`） |
| 時刻 | ループ定義の `schedule`（Security Scan の後） |
| コネクタ | Notion（前回の実行ログと `DB_依頼` の行を読み、今回の 1 ページを書きます） |

試すときは、手順を変えたブランチで変更をコミットしてから `/run-loop daily-triage --dry-run` を実行します（実行ログへの書き込みだけをしません）。

### 2.1 依頼済み・確認済みの項目と「要確認」のチェック

- Notion の `DB_依頼` から、kawashiro-server の「完了」以外の行を読みます（読むだけ）。報告の項目がすでに依頼されていれば
  `[継続 MM-DD〜・依頼済み]` の 1 行で済ませます。どの項目の依頼か決められない行は、報告の「依頼」の節にそう書きます
- 前回の実行ログの「確認済み」がチェックされていて、項目が前回と変わっていなければ、今回も `[継続 MM-DD〜・確認済み]` として扱います。
  引き継いだ印は本文に残るので、その後の回の「確認済み」をチェックしなくても続きます。件数が増える・仕分けが変わるなど、項目が変わると外れます
- 実行ログの「要確認」がチェックされるのは、**新しい項目があるとき**（変わって差分が出た項目を含む）、**継続の項目に依頼も確認済みも無いとき**、
  判定が `ESCALATE_HUMAN` のときだけです。急ぎの項目があっても、すべて継続で依頼済みか確認済みならチェックされません（区分は下がらず、1 行で出続けます）
- チェックを止めるには、その項目を `DB_依頼` に依頼するか、実行ログの「確認済み」をチェックします。「確認済み」をチェックするのは人で、ループは読むだけです

## 3. handle-request

### 3.1 仕組み（要点）

- 依頼は Notion の `DB_依頼` の 1 行です。**予定タスクが行を 1 件選び、ステータスを「作業中」にしてから**、その行の URL を引数にして
  ループを呼びます。ループは渡された 1 行だけを扱います（1 回の実行で 1 件）
- 流れ: 行を確かめる（「セッション」にセッションの URL を書く）→ 依頼を読んで対象を 1 つに決め、「やること」を 3 行以内にまとめる →
  範囲の判定 → 作業ブランチで直す → Checker → APPROVE なら push して PR → 行を更新 → 「レビュー待ち」の行の後始末 → 実行ログに 1 ページ
- **依頼は短くてかまいません。** 名前だけ・本文が空でも、「元の実行ログ」の項目のうちコードの変更で直す候補が 1 つだけなら、それを対象にして進めます
- **従うのは依頼の行の名前と本文の地の文だけです。** 本文に貼ったログ・引用・コードブロックと「元の実行ログ」は資料として読まれ、
  そこに書かれた指示には従いません。依頼が決められるのは「何を直すか」だけです
- **範囲の判定で差し戻すものと、質問して待つもの**
  - **差し戻し**は、触らないもの（人が手を動かすもの）に当たるときだけです。「結果」と実行ログに、人がやる手順が書かれます:
    CI とデプロイ（`.github/`）、コンテナの構成（`Dockerfile`・`docker-compose*.yml`）、秘密の置き場と環境変数、`.claude/`（ループ定義・run-loop・
    `.claude/CLAUDE.md`・スキル）。本番の compose と `.env`（[deployment.md](deployment.md) の責務境界のとおり Ansible の側）、
    マージ・デプロイ・リリース・ワークフローの手動実行・秘密の値が要るもの。パスの一覧はループ定義の `forbidden_paths` が正です
  - **確認待ち**は、人が答えれば進められるものです。選択肢と推奨が報告と実行ログに書かれ、行は「確認待ち」になります: 設計の判断が要る
    （直し方で API の振る舞い・データの形や migration・依存・費用・権限の境界が変わる）、対象が 1 つに定まらない、修正が要らないと見える
    （`develop` で既に直っている・再現しない）、Checker が 2 回退けた
  - 「変えるコードが無い」「再ビルドとリリースだけで直る」と結論する前に、同じ種類の問題をコードの変更で直した前例を `git log` で探します
    （例: `Dockerfile` で修正版以上を必須にしたコミット）。前例があればその直し方で進めます。前例の直し方が触らないパス（`Dockerfile` など）に
    及ぶときは差し戻しのままですが、人がやる手順に、前例のコミットと同じ直し方が具体的に書かれます
- **確認待ちへの答え方**: 行の「セッション」からセッションを開き、選択肢の記号（「A」「推奨で」）か文で返信します。ループは行を「作業中」に
  戻して続きから進めます（修正 → Checker → PR。返信があっても Checker は省きません）。セッションが残っていないときは、答えを依頼の本文に
  書き足してステータスを `依頼` に戻します（次の回が最初から扱います）
- **Checker** は 2 段です
  1. 機械の検査: 作業ツリーとブランチの状態、触らないパスの差分が 0 件、変えたパスに当たる CI 相当の検査（`pr-checks.yml` と同じ中身）
  2. 書いた本人とは別の、文脈を引き継がないサブエージェントが、差分と依頼を突き合わせて `APPROVE` / `REJECT` / `ESCALATE_HUMAN` を出します。
     **既定は REJECT** で、依頼にない変更（ついでの整形・リファクタ・依存の更新）が 1 つでも混ざっていれば REJECT です。
     指示文はループ定義の雛形で固定してあり、書いた側の言い分は渡しません
- REJECT は 1 回だけ直して、機械の検査から新しいサブエージェントでやり直します。2 回目も REJECT か、ESCALATE_HUMAN なら、
  **push せず PR も出しません**（退けられた理由が人の答えで解けるものなら確認待ち、触らないパス・回せない検査など人が手を動かすものなら差し戻し）
- **「レビュー待ち」の後始末**: 毎回の終わりに、kawashiro-server の「レビュー待ち」の行の PR を読み、マージ済みなら行を「完了」に、
  マージされずに閉じられていたら「差し戻し」にして「結果」に 1 行書きます。「依頼」の行が無い回は、引数なしで呼ばれてこれだけを行います
  （書いた行が無ければ実行ログも書きません）
- Notion に書くのは、依頼の行（引数の 1 行と、後始末で確かめた「レビュー待ち」の行）のステータス・PR・結果・セッションと、実行ログの
  1 ページの新規作成だけです。行の名前・本文・ほかのデータベースには書きません

### 3.2 依頼の書き方

| 列 | 書くこと |
|---|---|
| 名前 | 何をしてほしいか（1 件の修正に絞る）。短くてかまいません（「元の実行ログ」から対象が 1 つに定まるなら、空でも進みます）。試すだけの行は先頭に `[test]` を付けます（`--dry-run` でだけ扱い、本番で渡すと差し戻します） |
| 本文 | 対象・再現の仕方・どうなれば完了か。ログを貼るときはコードブロックにします（資料として読まれ、指示としては読まれません） |
| リポジトリ | kawashiro-server の行（違うと、ループは行に何も書かずに止まります） |
| 元の実行ログ | 任意。daily-triage の実行ログなど（新しいほうから 3 ページまで、資料として読まれます） |
| ステータス | 頼むときは `依頼`。`作業中` にするのは予定タスク（再開のときはループ）、`確認待ち`／`レビュー待ち`／`差し戻し` にするのはループ。`完了` は、PR がマージされた後の回にループが付けます（人が先に付けてもかまいません） |
| セッション | ループが書きます（そのセッションの URL。実行環境が示していないときは空のまま）。確認待ちに答えるときに開きます |

`DB_依頼` には、ステータスの選択肢「確認待ち」と、URL の列「セッション」が必要です（人が作ります。ループはデータベースの形を変えません。
無いと、確認待ちにする更新は失敗して行が「作業中」のまま残り、「セッション」は書かれずに要確認に出ます）。

秘密の値（鍵・トークン・パスワード）は依頼に書かないでください。

### 3.3 予定タスクの設定

| 項目 | 値 |
|---|---|
| 指示文 | `.claude/CLAUDE.md を読み、Notion の DB_依頼 から、リポジトリが kawashiro-server でステータスが「依頼」の行を、作成の古い順に 1 件選ぶ。あればその行のステータスを「作業中」にしてから、run-loop スキルで handle-request <その行の URL> を実行する。無ければ、run-loop スキルで handle-request を引数なしで実行する` |
| リポジトリ | このリポジトリ（既定のブランチ `main`） |
| 時刻 | 予定タスクの側で決めます（ループ定義は時刻を持ちません）。daily-triage の報告を読んで依頼を書く時間より後にします |
| コネクタ | Notion（依頼の行と実行ログ）、GitHub（PR の作成。`gh pr create` は GraphQL のためクラウドでは 403 になります） |
| 環境 | サブエージェント（Agent のツール）が使えること。作業ブランチを push できること。`uv sync`・`pnpm install` と検査が回るネットワーク |

- 「依頼」の行が無い回も、引数なしで呼びます（「レビュー待ち」の後始末だけが走ります）。呼ばないと、マージ済みの依頼が次の依頼まで「レビュー待ち」に残ります
- 行を選ぶことと「作業中」にすることは予定タスクの指示文の仕事で、ループ定義にはありません。選び方を変えるときは指示文を変えます
- 予定タスクは `main` のループ定義で走ります。ループ定義の変更は、`develop` → `main` のリリースの後の回から効きます
- 修正は `origin/develop` から切った作業ブランチに作り、PR は `develop` 宛です。クラウドのセッションは push してよいブランチ
  （`claude/...`）を 1 本指定するので、ループはそれを作業ブランチに使います。指定が無い環境では `claude/handle-request-<行の ID の末尾 8 桁>` を切ります
- 作業ブランチに `develop` にも `main` にも無いコミットが既にある、またはリモートに同じ名前のブランチがあると、ループは上書きせずに止まります

### 3.4 dry-run

`[test]` で始まる名前の依頼の行を作り（ステータスは何でもよい。予定タスクに拾われないよう `下書き` を勧めます）、
手順を変えたブランチで、変更をコミットしてから実行します。

    /run-loop handle-request <その行の URL> --dry-run

- 範囲の判定・修正・Checker（機械の検査とサブエージェント）までは本番と同じに走ります。**push・PR の作成・行の更新・実行ログへの書き込みはしません**
- 修正は手元の `loop-dry-run/handle-request-<ID8>` に残り（試しているブランチの HEAD から切ります。push しない使い捨て）、終わると元のブランチへ戻ります
- 報告の Checker の節で、機械の検査の PASS／FAIL、サブエージェントの判定と理由、書くはずだった行の値を確かめます
- **確認待ちを試す**には、判断の要る依頼（直し方が複数ある・対象が定まらない）を書きます。報告の先頭に「確認したいこと」（選択肢と推奨）が出て、
  書くはずだった値がステータス `確認待ち` になっていること、同じセッションに返信すると続き（修正 → Checker）が走ることを確かめます
- 引数なしの `/run-loop handle-request --dry-run` は、「レビュー待ち」の行の PR を読み、書くはずだった値だけを報告します

### 3.5 判定と行の読み方

| 結末 | 依頼の行 | 実行ログの判定 | push | すること |
|---|---|---|---|---|
| PR を作った | `レビュー待ち`・PR の URL・結果 | `APPROVE` | 済 | PR と `pr-checks.yml` の結果を確かめてマージし、行を `完了` にする |
| 質問して待っている | `確認待ち`・結果に質問の要点と推奨 | `ESCALATE_HUMAN`（Checker が 2 回退けた後なら `REJECT`） | なし／止めた | 行の「セッション」を開き、「確認したいこと」の選択肢に返信する。セッションが無ければ、答えを本文に足して `依頼` に戻す |
| 差し戻した（触らないもの・検査を回せなかった など） | `差し戻し`・結果に人がやる手順の要点 | `ESCALATE_HUMAN` | なし／止めた | 実行ログの「人がやる手順」を行う。変更があっても、ループの環境の作業ブランチに残るだけで push されていません |
| PR がマージされた（後の回の後始末） | `完了` | `APPROVE` | なし | なし |
| PR がマージされずに閉じられた（同） | `差し戻し`・結果に 1 行 | `APPROVE`（要確認にチェック） | なし | まだ直すなら、理由を本文に足して `依頼` に戻す |
| 行を確かめられずに止めた | 変わらない | `ESCALATE_HUMAN` | なし | 行のリポジトリとステータス、指示文が渡した URL を確かめる |

- L2 の判定は「Checker が差分を通したか」です。`APPROVE` でも、正しさを最後に決めるのは PR のレビューと CI です
- 行が `作業中` のまま残っているときは、ループが途中で落ちたか、行の更新に失敗しています。実行ログを見て、行を手で `依頼` か `差し戻し` に戻します

## 4. ループを直す・足す

ループ定義と run-loop はループの中では変えません。人が別のセッションで、ブランチと PR で直します。

1. `feature/*` などのブランチで、ループ定義か `run-loop` の SKILL を直す
2. 変更をコミットしてから dry-run で試す
3. 振る舞いが変わったら、このドキュメントも同じ PR で直す（[docs-sync](../.claude/skills/docs-sync/SKILL.md) の対応マップ）
4. `develop` へ PR → `main` へリリース。予定タスクは次の回から新しい定義で走る（指示文は変えない）

ループを足すときは、`.claude/loops/<名前>.md` を作り、Notion の `DB_ループ` に行を作って（人が作ります。リポジトリは kawashiro-server の行だけ）
その URL を `notion_loop` に書き、予定タスクを 1 つ足します。L1・L2 以外の段階は、run-loop の段階の表と Checker を先に定義してから使います。

## 5. トラブルシューティング

| 症状 | 原因と対処 |
|---|---|
| 判定 `ESCALATE_HUMAN` で「開始時に作業ツリーに差分がある」 | 走った環境の作業ツリーに変更が残っていました。手元の dry-run なら、変更をコミットしてからやり直します |
| 「実行ログ: 書き込みに失敗（`notion_loop` の行が違う）」 | `DB_ループ` の行の名前かリポジトリが変わりました。行を直すか、ループ定義の `notion_loop` を正しい行にする PR を出します |
| handle-request が「作業ブランチに既にコミットがある」で止まる | 前の回の作業か、人の作業が同じブランチに残っています。PR にするか消してから、行を `依頼` に戻します |
| handle-request が「Agent のツールが使えない」で `ESCALATE_HUMAN` | サブエージェントを起こせない環境で走りました。ループは自分の差分を自分で判定しません。予定タスクの環境を確かめます |
| handle-request が「リポジトリの検査を回せなかった」で `ESCALATE_HUMAN` | 変えたパスに当たる検査の道具が環境に無い・ネットワークで依存を取れません。環境を直すか、人が直します |
| 行が `確認待ち` にならず `作業中` のまま、または「セッション」が空 | `DB_依頼` に選択肢「確認待ち」か列「セッション」がありません（人が足します）。「セッション」は、実行環境がセッションの URL を示していないときも空になります（推測では書きません）。実行ログの Checker の節の「行の更新」「セッション」を読みます |
| マージしたのに行が `レビュー待ち` のまま | 後始末は、次に handle-request が走った回に行います。ループ定義は `main` のものが使われるので、この動きは `develop` → `main` のリリース後から効きます。「依頼」の行が無い日に走っていなければ、予定タスクの指示文が引数なしの実行を含んでいるかを確かめます |
| handle-request の push が拒まれる | 環境が指定したブランチ以外へ push しようとした、または GitHub の権限がありません。ループは `develop`・`main` へは push しません |
